前段时间，我想改一下 B 站个性签名。

随手写了一句话，又加了几个 emoji，自我感觉还不错，点下保存，结果弹出一个提示：

> 修改个性签名失败：签名最多支持70个字！

我当时愣了几秒，盯着那行字数看了半天。

中文、英文、标点，再加四五个 emoji，怎么看都不像有 70 个字。重新数了一遍，三十多个，撑死四十。

难道空格没删干净？检查了一遍，没有。

于是我把那些花里胡哨的 emoji 删掉，再试一次——通过了。

嗯？删掉 emoji 就通过了？

我脑子里突然冒出一个问题：

**难道一个 emoji，在 JavaScript 里不算一个字？**

打开控制台。

```js
'👍'.length // 2
```

**好家伙，一个竖大拇指，长度居然是 2。**不服，再来一个。

```js
'👨‍👩‍👧‍👦'.length // 11
```

11。

**那问题来了——`.length` 到底在数什么？**

为了回答这个问题，我们得一路往下追。

---

## 字符编码简史

要追这个问题，得先回到一个更基础的起点。

很多人第一次接触字符串时，都会有一个很自然的想法：

> 字符串，不就是字符组成的吗？

**可对于计算机来说，其实并不存在什么「字符」，它认识的只有数字。**

你输入 `ABC`，在你眼里是三个字母；对 CPU 来说，则是三个数字。

问题来了——字母 A 为什么对应这个数字，而不是另一个？总得有一张映射表，规定 A 是多少、B 是多少、C 是多少。

这种把字符映射到数字编号的规则，就叫字符集（Character Set）。

最早被广泛使用的是 ASCII。

比如：

| 字符 | ASCII 码 |
|------|---------|
| A | 65 |
| B | 66 |
| C | 67 |

一共只有 128 个字符。

对英语世界来说，勉强够用了。

**可世界不只有英语。中文怎么办？日文怎么办？数学符号怎么办？很快，这 128 个位置就不够用了。**

于是各个国家和地区开始设计自己的编码方案。中国有 GB2312、GBK；日本有 Shift-JIS；台湾有 Big5。

大家都试图把本地语言表示成数字。

**可问题也随之而来——同一串二进制数据，在不同编码方案下，可能对应完全不同的文字。于是那个著名的乱码时代来了。**

我记得大学时玩《三国志 11》，想给武将起个中文名。游戏使用的是 Big5 编码，系统默认却是 GBK。同样一串二进制数据，拿两张不同的表去查，出来的字完全不一样，结果满屏乱码。那个年代，这种事情几乎天天发生。

---

## Unicode：一张全球统一的大表

乱码问题折腾到一定程度，终于有人站出来说：

**别各搞各的了。我们做一张全球统一的大表。**

这张表，就是 Unicode。

Unicode 做的事情其实很单纯。

它不规定字符长什么样。

也不规定字符怎么存储。

它只负责一件事：

> **给每一个字符分配一个唯一编号。**

这个编号叫码点（Code Point）。

例如：

| 字符 | 码点 |
|------|------|
| A    | U+0041 |
| 好   | U+597D |
| 👍   | U+1F44D |
| 😂   | U+1F602 |

这个 `U+`，你可以简单理解成：

> 这是一个 Unicode 码点。

于是，全世界终于拥有了一套统一的字符身份证系统。

但这一步还只是编号，跟存储是两回事。

Unicode 只负责分配码点，至于这些码点如何放进内存、文件或网络数据流，则交给 UTF-8、UTF-16、UTF-32 这样的编码方案去处理。

这里一定要区分两个非常容易混淆的概念：

- **码点（Code Point）回答「它是谁」**
- **UTF 编码回答「它怎么存」**

光会区分还不够，还得知道现实世界到底在用哪一套——现代 Web、数据库以及绝大多数文件系统，几乎都使用 UTF-8 进行存储和传输。而 JavaScript 引擎内部使用的却是 UTF-16。

---

## 为什么 JavaScript 用 UTF-16

那么问题来了——为什么 JavaScript 要使用 UTF-16？

故事得回到 1995 年，也就是 JavaScript 诞生的那一年。

当时 Unicode 里的字符，绝大多数都集中在 0 到 65535 这个范围内，一个 16 位整数刚好能够装下。于是大家觉得：拿 16 位作为基本存储单元，不是挺好吗？

Unicode 给这个基本存储单元起了个名字：

> 码元（Code Unit）

后来，0 到 65535 这片区域也有了正式名称：

> BMP（Basic Multilingual Plane，基本多文种平面）

站在 1995 年那个时间点看，六万多个位置已经多得离谱，所以 JavaScript 选择 UTF-16，其实是一个非常合理的工程决策。

当时的世界看起来非常整齐。

> **一个字符 ＝ 一个码点 ＝ 一个码元**

| 字符 | 码点 | UTF-16 码元 |
|------|------|-------------|
| A    | U+0041 | `0x0041` |
| 好   | U+597D | `0x597D` |

大家都遵循同一套规则，没有任何问题。

问题出在后来。

Unicode 开始疯狂扩张——历史文字、古文字、数学符号、乐谱符号、emoji，新的字符不断加入。

码点范围一路扩展到了 `U+10FFFF`：

这里有一个特别容易误解的地方：`U+10FFFF` 并不是说 Unicode 已经定义了一百多万个字符，它表示的是：

> Unicode 码点空间允许的最大上限。

整个空间总共能容纳 1,114,112 个码点。

这么大一片码点空间，UTF-16 拿 16 位的码元怎么装得下？16 位最多只能表示 `0x0000 ~ 0xFFFF`，也就是六万多个值。怎么办？推倒重来？不现实。

于是 UTF-16 选择了另一条路——打补丁。

这个补丁叫：

> Surrogate Pair（代理对）

---

很多人第一次接触代理对时，会觉得特别复杂。其实如果把历史背景都拿掉，它的规则简单得出奇，只有两条。

第一条：

如果码点位于 `U+0000 ~ U+FFFF`，也就是 BMP 内部。

直接使用一个 16 位码元表示。

例如：

| 字符 | 码点 | UTF-16 码元 |
|------|------|-------------|
| A    | U+0041 | `0x0041` |
| 好   | U+597D | `0x597D` |

一个码点对应一个码元，非常简单。

第二条：

如果码点超过 U+FFFF。

例如：

| 字符 | 码点 |
|------|------|
| 👍 | U+1F44D |

一个码元已经放不下，那就使用两个码元一起表示。这就是代理对。

Unicode 专门预留了两段区域给 UTF-16 使用：

| 区域 | 十六进制 | 十进制 |
|------|---------|-------|
| 高代理（High Surrogate） | `0xD800` ~ `0xDBFF` | 55296 ~ 56319 |
| 低代理（Low Surrogate） | `0xDC00` ~ `0xDFFF` | 56320 ~ 57343 |

这些值本身不是字符。

Unicode 虽然给它们分配了编号，但明确规定：

> **它们永远不对应任何字符。**

它们只是 UTF-16 编码机制内部使用的零件，必须满足两个条件才能表示一个真正的字符：

1. **必须成对出现**，不能落单
2. **必须是高代理在前、低代理在后**，顺序不能颠倒

不满足的就是非法 UTF-16。

---

但 JavaScript 并不强制这两条规则。

很多文章都说"JavaScript 使用 UTF-16"，这话不算错，但容易让人误会——仿佛 JavaScript 字符串天然就是合法 UTF-16 似的。

ECMAScript 对字符串的定义其实极其朴素：

> **字符串是一串有序的 16 位无符号整数。**

只有结构，没有合法性约束。

所以下面这种在 UTF-16 世界里纯属非法的数据——只有高代理，没有低代理：

```js
'\ud800'
```

在 JavaScript 里依然是合法字符串：

```js
'\ud800'.length  // 1
```

不报错，不修复，也不补代理。

**因为 JavaScript 眼里根本没有「非法代理」这回事——它看到的只是一个普通整数 `0xD800`。**

---

为什么这么设计？

JavaScript 经常要处理各种未经验证的原始数据：网络字节流、截断的文本、损坏的文件、遗留的编码。如果每次构造字符串都校验 UTF-16 合法性，兼容性和性能都会打折。

所以 ECMAScript 索性：

> **允许不合法代理序列存在。**

检查与否，交给开发者自己决定。

ECMAScript 2024 也补了两个相关方法：

```js
str.isWellFormed()
str.toWellFormed()
```

前者判断字符串是否为合法 UTF-16，后者把非法代理替换成替换字符 �。

## JavaScript 操作的是码元

铺垫够了。回头看 👍。它的码点 U+1F44D，超过 BMP 了，UTF-16 拿两个码元来装：

```text
0xD83D  高代理
0xDC4D  低代理
```

| 层级 | 值 |
|------|------|
| 字符 | 👍 |
| 码点 | U+1F44D |
| UTF-16 码元 | `0xD83D` `0xDC4D` |

两个码元。注意：👍 没有被拆成两个字符，它始终是一个字符，只是 UTF-16 需要两个码元才能装下。这个区别非常重要。

好，现在看 `.length`：

```js
'👍'.length
// 2
```

为什么？**因为 JavaScript 数的不是字符，它数的是码元。**

👍 对应两个码元：

```text
👍  (U+1F44D)
├─ 0xD83D  ← High Surrogate
└─ 0xDC4D  ← Low Surrogate
   ─────────
   .length = 2 （两个码元）
```

所以长度是 2。

`.length` 只干一件事：

> **统计字符串里有多少个 UTF-16 码元。**

它不关心这是一个字符，也不关心这是半个代理，它只负责数码元。

所以，记住一句：

> **JavaScript 操作的是码元。**

弄清楚了这一点，再看那些经典的字符串 API，一切就说得通了。

例如 `'👍'[0]` 得到 `'\ud83d'`。为什么？

因为第 0 个码元就是高代理。

注意，`[0]` 返回的是字符串，拿到的是 `'\ud83d'` —— 码元 `0xD83D` 的字符串形式。

再看 `'👍'[1]` 得到 `'\udc4d'`，也就是低代理。

JavaScript 并不知道这两个东西应该拼起来。

它只是机械地按照下标取值。

第 0 个。

第 1 个。

仅此而已。

再看 `'👍'.charCodeAt(0)` 返回 `55357`（`0xD83D`）。

这个 API 的名字其实有点历史包袱。

它叫 `charCodeAt`。

很多人会下意识觉得：

> 返回字符编码。

实际上返回的却不是 Unicode 码点。

而是当前位置那个 UTF-16 码元的值。

所以拿到的仍然是高代理：`0xD83D`。

切片也是同样的逻辑。

例如 `'AB👍CD'.slice(2, 3)` 得到 `'\ud83d'`。为什么？

因为内存里的布局实际上是：

| 索引 | 码元 |
|------|------|
| 0 | A 的码元 |
| 1 | B 的码元 |
| 2 | 0xD83D |
| 3 | 0xDC4D |
| 4 | C 的码元 |
| 5 | D 的码元 |

`slice(2, 3)` 只切到了第三个码元。

自然只能得到半个代理。

必须这样：

```js
'AB👍CD'.slice(2, 4)
```

才能同时拿到 `0xD83D` 和 `0xDC4D`，重新拼成 👍。

到这里你会突然发现一件事：**这些 API 从来都没有真正操作过「字符」。它们操作的始终是：UTF-16 码元序列。**

之所以过去没觉得有问题，是因为在 BMP 时代，一个字符恰好等于一个码元，于是大家误以为这些 API 是在操作字符。**直到 emoji 出现，这条隐藏了二十多年的设计边界才第一次暴露出来。**

---

## ES6：码点视角

如果说 ES5 的 JavaScript 世界里只有一种单位——码元（Code Unit），那么 ES6 引入了另一种视角——码点（Code Point），并基于此提供了一套新工具。

首先是新的 Unicode 字面量写法。ES5 时代，如果你想表示一个补充平面的字符，通常只有两种办法。

第一种：直接把 emoji 粘进去，`'👍'`，简单，但不一定看得出具体码点。

第二种：手写代理对，`'👍'`，更难读。

于是 ES6 增加了 `'\u{1F44D}'`，直接按码点书写，可读性好了很多。

不过要注意：这只是语法层面的改进，底层并没有发生变化。

JavaScript 内部依然会把它转换成两个 UTF-16 码元存储：`0xD83D 0xDC4D`。

真正重要的变化，是字符串迭代器（String Iterator）。

假设：

```js
const str = '👍A';
```

它在内存里的样子是 `[0xD83D, 0xDC4D, 0x0041]`。

ES5 时代如果这样遍历：

```js
for (let i = 0; i < str.length; i++) {
  console.log(str[i]);
}
```

一个 emoji 被拆成了两次访问。

ES6 直接重新定义了字符串遍历规则：字符串迭代器必须按码点遍历，而不是按码元遍历。

于是：

```js
for (const ch of '👍A') {
  console.log(ch);
}
```

分别输出 `👍` 和 `A`。

为什么？因为迭代器看到 `0xD83D`，先判断这是高代理，然后再看看下一个码元 `0xDC4D`，发现是合法低代理，于是自动按照 UTF-16 规则把两者组合成码点 `U+1F44D` 作为一次迭代结果返回。

这件事的影响其实非常大，因为受影响的不只是 `for...of`，还有很多你已经在用的语法，比如展开运算符。

```js
[...'👍']
```

结果是 `['👍']`，长度是 `1`。

为什么？因为展开运算符自己并不遍历字符串，它调用的是字符串迭代器，而字符串迭代器已经变成了按码点遍历，所以两个码元会自动合并成一个字符。

`Array.from()` 也一样——它依赖的是 iterable protocol，本质上还是那套 ES6 String Iterator。

迭代器解决了遍历问题。可如果你不想遍历整串字符，只是想直接拿某个位置对应的码点呢？ES6 `codePointAt()` 就是干这个的。

同样的位置，ES5 `charCodeAt(0)` 只拿到高代理 `0xD83D`，而 `codePointAt(0)` 返回的却是真正的 Unicode 码点：`0x1F44D`

它是怎么做到的？其实也不神秘。`codePointAt()` 并没有改变 JavaScript 底层的存储方式，它依然面对同样的 UTF-16 码元序列，区别只是它会主动解析代理对。

看到当前位置是高代理 `0xD83D`，它会继续往后看。

如果下一个码元是合法低代理 `0xDC4D`，那就按照 UTF-16 的规则把两者重新组合。

最终得到 `U+1F44D`，返回给你。

反过来也一样。ES5 有 `String.fromCharCode(0xD83D)`，结果得到的是半个代理 `'\ud83d'`，因为它根本不知道你想表示什么字符，只会机械地把这个数字当作一个码元塞进字符串。

ES6 则新增了 `String.fromCodePoint()`——例如 `String.fromCodePoint(0x1F44D)`，直接得到 `👍`。

因为它操作的是码点，而不是码元。

这里还有一个很容易被忽略的小细节。

`String.fromCodePoint(0xD800)` 会直接抛出 `RangeError`。

很多人第一次看到都会愣一下。

不是说 `0xD800` 也是 Unicode 码点吗？

为什么不能用？

原因前面已经说过。

`0xD800 ~ 0xDFFF` 属于代理区。

Unicode 虽然给它们分配了编号，但明确规定：

> **它们永远不对应任何字符。**

它们只是 UTF-16 内部使用的编码零件。

而 `fromCodePoint()` 要求传入的是真正的字符码点。

代理区码点不满足这个条件，所以直接抛 `RangeError`。

说到这里，Unicode 里其实还藏着一个更精确的概念——Unicode Scalar Value（Unicode 标量值）。

很多文章讲到这里都会把人绕晕，其实一句话就够了：**Unicode 标量值，就是那些真正能够表示字符的码点。**

换句话说：**所有 Unicode 码点减去代理区码点**，剩下的就是 Unicode 标量值。

写成范围大概是 `U+0000 ~ U+D7FF` 和 `U+E000 ~ U+10FFFF`。

中间那段 `U+D800 ~ U+DFFF` 被整个挖掉了，因为那部分永远只是 UTF-16 的内部机制，不是真正的字符。

从严格意义上讲，ES6 这套 Unicode API 实际操作的对象并不是全部码点，而是 Unicode 标量值，只是名字没有刻意强调而已。

例如 `String.fromCodePoint()` 拒绝代理码点，而 `codePointAt()` 遇到合法代理对时会自动解析出一个标量值。本质上都站在同一层。

不过从实际开发角度来说，不用太纠结这个概念，记住一句话就够了：代理码点不是字符。

当你在处理 Unicode 字符时，真正面对的对象其实都是 Unicode 标量值。

到这里，ES6 的 Unicode 工具箱基本齐了：

- `\u{...}` — 直接按码点书写字符
- `for...of` — 按码点遍历字符串
- `Array.from()` — 自动识别代理对
- `codePointAt()` — 拿到真正的 Unicode 码点
- `fromCodePoint()` — 根据码点生成字符

看起来问题已经解决了。现在：

```js
'👍'.length
// 2
```

是码元层，而：

```js
[...'👍'].length
// 1
```

已经变成码点层。

似乎终于可以放心地说：一个字符就是一个码点。可惜，因为很快你就会遇到这个家伙：

```js
'👍🏻'
```

然后发现 `[...'👍🏻'].length` 是 `2`。

**等等——不是已经按码点数了吗？为什么还是 2？**

更离谱的是，`'👨‍👩‍👧‍👦'` 的 `[...'👨‍👩‍👧‍👦'].length` 是 `7`，可人眼看到的明明只有一个家庭 emoji。

问题到底出在哪？

---

## 码点 ≠ 视觉字符：多码点组合

答案是：

> **码点依然不是人眼理解的那个「字符」。**

**一个视觉字符，完全可能由多个码点共同组成。**先看最简单的例子 `'👍🏻'`。

这是一个浅肤色的大拇指。人眼看到的是一个 emoji，可它实际上由两个码点组成：👍（U+1F44D）+ 🏻（U+1F3FB，肤色修饰符）。组合起来之后渲染器才会显示成 👍🏻。

因此 `[...'👍🏻'].length` 是 `2`——完全正确，因为它确实有两个码点。

这就是 Unicode 的第二个大坑：码点 ≠ 视觉字符。也是很多人第一次接触时最容易懵的地方。

类似的例子还有很多——国旗。`'🇨🇳'` 看起来是一个中国国旗，实际上是两个区域指示符拼出来的：🇨 + 🇳。因此 `[...'🇨🇳'].length` 是 `2`，依然成立。

再来一个更离谱的——家庭 emoji。`'👨‍👩‍👧‍👦'` 人眼看到的是一个完整家庭，可内部其实是多个码点通过 ZWJ（零宽连字符）连接而成：

👨 + ZWJ + 👩 + ZWJ + 👧 + ZWJ + 👦

其中 ZWJ = Zero Width Joiner = U+200D，本身不会显示任何东西，作用只有一个：告诉渲染器，前后两个字符不要分开画，把它们连成一个整体。

除了多个码点组合成一个新字符，还有一类更特殊的组合——码点本身不变，只是加一个控制码点来切换显示风格。Variation Selector（变体选择符）就干这个。

最常见的例子是 VS16（U+FE0F），它告诉渲染器：用 emoji 风格显示前面那个字符。

比如 `'☀'` 是一个普通的太阳符号 U+2600，默认可能显示成文本样式。但如果你想要彩色 emoji 版本，就在后面加上 U+FE0F——于是渲染器收到指令，显示成 `☀️`。

所以 `'☀️'.length` 和 `[...'☀️'].length` 都是 `2`——它本来就是两个码点：一个字符加一个样式控制符。

区别在于：肤色修饰符是从一堆人中选一个肤色，VS16 是同一个东西用文本还是 emoji 风格显示。

从码元到码点，再到多码点组合——你已经追了两层，可离用户眼里的「一个字」还差得远。究竟什么才是人眼认知中的那个字符？

---

## 字素簇（Grapheme Cluster）

因为 Unicode 允许多个码点共同描述一个视觉单元，于是又引入了第三层，也是最接近人类认知的一层——Grapheme Cluster（字素簇），也叫用户感知字符。

这个名字听起来有点学术，其实意思特别简单。**它回答的问题是：人眼会把哪些东西看成一个字符？**

例如：`A` 是一个字素簇，`好` 是一个字素簇，`👍`、`👍🏻`、`👨‍👩‍👧‍👦` 也都各是一个字素簇。

无论里面塞了多少码点，只要用户会把它们当作一个字符，Unicode 就把它们划进同一个字素簇。

Unicode 对字素簇的划分有一整套正式规则，定义在 `UAX #29`（Unicode Text Segmentation）中。

这里面细节非常复杂，涉及上百条边界规则，绝大多数开发者没有必要手工实现，知道有这么一层存在就够了。

真正重要的是：JavaScript 终于提供了官方实现——`Intl.Segmenter`。

**如果说 `.length` 工作在码元层，`for...of` 工作在码点层，那么 `Intl.Segmenter` 工作在字素簇层——终于来到人眼认知的那一层了。**

例如：

```js
const seg = new Intl.Segmenter('zh', { granularity: 'grapheme' });
[...seg.segment('👨‍👩‍👧‍👦')].length
// 1
```

结果终于变成了 `1`，和人手数出来的结果完全一致。

更实用的不只是统计数量，还能真正把字符切出来。

例如：

```js
const seg = new Intl.Segmenter('zh', { granularity: 'grapheme' });
const clusters = [...seg.segment('A👍🏻B')];
clusters.map(c => c.segment)
// ['A', '👍🏻', 'B']
```

注意 `👍🏻` 被完整保留下来了——不会拆成 `['A', '👍', '🏻', 'B']`，也不会切回代理对。因为在字素簇层，它本来就是一个整体。

这也是为什么。如果你要做：

- 字数统计
- 输入框限制
- 文本截断
- 打字机动画
- 光标移动
- 删除一个字符

这些直接面向用户的功能。

**最靠谱的单位其实不是码元，也不是码点，而是字素簇。**

因为用户认知里的「一个字」**本质上就是一个 Grapheme Cluster**。

## normalization：字符的"AB 面"

故事发展到这里，看起来终于抵达终点了。**可 Unicode 最喜欢干的一件事就是：当你觉得自己已经理解它的时候，再给你挖一个新的坑。**

因为接下来我要告诉你：**两个看起来完全一样的字符，在 JavaScript 里居然有可能不相等。**

比如 `é`，居然有两种完全不同的表示方式，视觉上却一模一样。一个 `'é'.length` 是 `1`（U+00E9），另一个 `'e\u0301'.length` 是 `2`（U+0065 + U+0301）。

**肉眼完全分不出，连字体渲染都一样，可 JavaScript 斩钉截铁告诉你——它俩不是同一个字符串。**

问题出在编码方式不同。第一个 é 是预组合字符，一个码点到位：`U+00E9`；第二个 é 是分解形式，先写 e，再叠锐音符：`U+0065 + U+0301`。

两套码点序列，**`===` 比的是序列，不是长相。**序列不同，结果自然是 false。Unicode 管这个叫「规范等价」——视觉一致，底层不同，但标准承认它们等价。可等价归等价，比较、查找、去重，照样全踩坑。

怎么让它俩相等？`normalize()` 就是干这个的。默认用 NFC，把分解序列合并成单码点，也可以用 NFD 反过来拆开。

实际开发里，拿不准用户输入用了哪种形式，存之前先 normalize 一下。不然去重数组时，明明看着俩重复项，就是去不掉——这种 bug 够你查半天。

还有个坑：`normalize()` 除了 NFC 和 NFD，还有 NFKC 和 NFKD。这俩不只是统一格式，会直接改文本语义。比如 `①` → `1`，`㎏` → `kg`。

搜索匹配时 NFKC 很顶用。但你要是只想规范组合方式、不想丢语义，老老实实用 NFC。

不过 `normalize()` 也有自己的边界——全角 `Ａ` 和普通 `A` 视觉接近？Unicode 眼里是两码事，normalize 不合并。

**追了这么远，以为终于到头了。结果这个坑，它填不到底，因为已经不归字符串模型管了。**

## 编码转换、正则

以上都是 JS 引擎内部的视角——码元、码点、字素簇。但字符串的完整生命周期远不止这些。

事实上，**JS 可能是唯一还在重度使用 UTF-16 的地方了。**Web、Linux、macOS、HTTP、JSON、数据库——几乎清一色 UTF-8，UTF-16 主要留在 JavaScript、Java、Windows API 这些有历史包袱的系统里。所以字符串在 Web 中的旅程通常是：存于磁盘或网络时是 UTF-8，进了 JS 引擎变成 UTF-16，出去又转回 UTF-8。

TextEncoder 和 TextDecoder 负责搭这座桥。好在绝大多数时候你不用手动调用它们——浏览器和 Node.js 在背后已经帮你处理了。

当你需要在 JavaScript 字符串和 UTF-8 字节之间转换时，就会用到 `TextEncoder` / `TextDecoder`：

```js
const encoder = new TextEncoder();
encoder.encode('你好').length; // 6 — UTF-8 字节数
'你好'.length; // 2 — UTF-16 码元数

const decoder = new TextDecoder();
decoder.decode(new Uint8Array([0xE4, 0xBD, 0xA0, 0xE5, 0xA5, 0xBD])); // '你好'
```

---

以上说的全是字符串自身的方法。正则也逃不掉同一个问题。

**默认 `/^.$/` 匹配的是码元，不是字符：**`/^.$/.test('👍')` 是 `false`，因为 👍 是两个码元。

加个 `u` flag，它才按码点走：`/^.$/u.test('👍')` 是 `true`。

有了 `u` flag，还能用 `\p{}` 按 Unicode 属性匹配，比如 `/\p{Script=Han}+/u.test('你好')` 是 `true`，`/\p{Letter}/u` 匹配所有字母。

到了 ES2024，又多了 `v` flag，专门对付复杂 emoji：`/^\p{RGI_Emoji}$/v.test('👨‍👩‍👧‍👦')`。不过 `v` flag 还太新，上线前得确认目标环境认不认。

## 尾声

回头看看这一路：码元、码点、字素簇、normalize、编码转换、正则——**每一层都是坑。**

**这件事，像极了巴别塔。**

**人类花了几十年，建起 Unicode 这座通天塔，想给世间每一个字符都发一张独一无二的身份证。塔确实立起来了，抬头望去，宏伟、统一、无所不包。**

**可仔细一瞅，同一个字在不同层面竟有四套长度，两个长得一模一样的字符串，站在 `===` 面前，居然被判为陌路。**

**它统一了。但统一底下，是另一套更复杂的、需要重新学会的「不统一」。**

再回头看那个 B 站签名框。

我几乎可以断定，那个「最多 70 个字」的限制，大概率就是一行 `input.value.length > 70`。换成我，第一次接到这种需求，大概率也这么写。

**就是这一行 `input.value.length > 70`，成了这座巴别塔墙壁上，我亲手摸到的第一条裂缝。**

**它告诉我，字符串这件事，比我想象的要深得多。**
