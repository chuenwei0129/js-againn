```javascript
const arr = [1, 2, 3, 4];
arr.length = 2;
console.log(arr);
// [1, 2]
```

这是每个 JavaScript 开发者都见过的一段代码。

但如果认真思考一分钟，就会发现，这件事其实有些反直觉。

我们只是执行了：

```javascript
arr.length = 2;
```

看起来只是把一个数字从 `4` 改成了 `2`，结果数组最后两个元素却真的消失了。

如果换成普通对象：

```javascript
const obj = {
  count: 4,
  a: 1,
  b: 2,
};

obj.count = 2;

console.log(obj);
// {
//   count: 2,
//   a: 1,
//   b: 2
// }
```

修改 `count` 不会影响任何其它属性。

为什么数组却可以做到**修改一个属性，整个对象结构都发生变化**？

很多人会回答：

> 因为 `length` 是特殊属性。

这当然没错。

但真正的问题其实不是：

> **为什么 `length` 特殊？**

而是：

> **为什么 ECMAScript 能赋予一个属性如此特殊的行为？**

换句话说，JavaScript 到底靠什么机制，让一次看似普通的属性赋值，最终变成了一整套复杂的对象操作？

真正决定对象行为的，并不是我们能够看到的 **Property（属性）**，而是 ECMAScript 对对象模型的三层抽象：

- **Property Descriptor**：描述每个 Property 的元数据；
- **Internal Slot（内部槽）**：对象保存内部状态的地方；
- **Internal Method（内部方法）**：对象真正执行各种操作时遵循的规范算法。

它们各自承担着不同的职责：

- Property 是对象对外暴露的接口；
- Property Descriptor 描述了这个接口的各种属性（是否可写、是否可枚举等）；
- Internal Slot 保存对象运行时的内部状态；
- Internal Method 则根据 Property Descriptor 与 Internal Slot 执行规范定义的算法。

对象的大部分行为，都可以从这四者的协作中得到解释。

理解了它们，你会发现：

- 为什么数组可以自动删除元素；
- 为什么对象拥有原型链；
- 为什么 Promise 能记住自己的状态；
- 为什么 Map 能维护键值；
- 为什么函数可以被调用。

这些看似毫不相关的语言特性，其实都建立在同一套对象模型之上。

---

## ECMAScript 的对象，并不只是属性

大多数开发者第一次接触 JavaScript 时，对对象的理解都是这样的：

```javascript
const person = { name: 'Tom', age: 20 };
```

正如上一篇所述，对象中的每个 Property 都对应着一份 Property Descriptor，而非简单的 Key-Value。但 Property Descriptor 仍然只是对象模型的一小部分。在 ECMAScript 规范中，一个对象更接近下面这种结构：

```text
Object
├── Properties
│   └── 每个 Property 对应一个 Property Descriptor
├── Internal Slots
└── Internal Methods
```

Properties 与 Property Descriptor 组成了对象对外暴露的数据接口，而 Internal Slot 与 Internal Method 则构成了对象内部的运行机制。

接下来，我们先从 Internal Slot 开始。

---

## Internal Slot：保存对象隐藏内部状态的地方

无论是 `person.name` 这样的 Property，还是描述它特征的 Property Descriptor，都属于对象对外暴露的接口层，开发者看得见、也摸得着。

但对象真正拥有的数据，并不只有这些。

ECMAScript 还规定，每个对象都拥有一些**无法通过 JavaScript 代码直接访问的内部状态**，规范把它们称为 **Internal Slot（内部槽）**。

可以把对象进一步表示成这样：

```text
Object
├── Properties
│   ├── name
│   │    └── Property Descriptor
│   ├── age
│   │    └── Property Descriptor
│   └── length
│         └── Property Descriptor
│
└── Internal Slots
    ├── [[Prototype]]
    ├── [[Extensible]]
    ├── [[PromiseState]]
    ├── [[MapData]]
    └── ...
```

注意，这里的 `[[Prototype]]`、`[[PromiseState]]` 等都不是 Property。

它们不会出现在对象的属性集合中，因此也不会参与任何属性相关的操作。例如 `Object.keys(obj)`、`Reflect.ownKeys(obj)`、`for...in` 都不会得到任何 Internal Slot。

甚至 `obj.[[Prototype]]` 本身就是非法语法，因为 `[[...]]` 只是 ECMAScript 规范描述内部状态的一种记号，并不是 JavaScript 提供的语法。如果写成：

```javascript
obj["[[Prototype]]"] = 123;
```

得到的也只是一个名字恰好叫 `"[[Prototype]]"` 的普通 Property，与真正的 `[[Prototype]]` 完全没有关系。

---

## 为什么叫 Slot？

你可能会好奇：为什么叫 Slot？

Slot 可以理解成**插槽、槽位、存储格**。这个名字其实很形象。

可以把一个对象想象成一栋房子。开发者每天接触的是客厅、书房、厨房，对应对象暴露出来的 Property。但一栋房子真正能够正常运行，还依赖很多住户平时根本不会接触的地方，例如配电间、设备间、水管井、弱电井。这些地方并不是给住户使用的，它们保存的是整栋建筑运行所需的内部状态。

Internal Slot 就类似这些区域。它们不是对象对外暴露的数据，而是对象自身运行所依赖的内部信息。

因此，可以把对象简单理解成两层：

```text
对象

├── Property
│     给开发者使用
│
└── Internal Slot
      给对象自己使用
```

---

## Internal Slot 保存的是什么？

不同的 Internal Slot 会保存不同的内部状态。

例如：

```text
[[Prototype]]
↓
保存当前对象的原型引用

[[Extensible]]
↓
保存对象是否允许继续扩展

[[PromiseState]]
↓
保存 Promise 当前状态
(pending / fulfilled / rejected)

[[MapData]]
↓
保存 Map 内部维护的键值记录
```

可以发现，这些 Internal Slot 保存的都不是对象对外暴露的数据，而是对象运行过程中所需要的内部信息。

事实上，几乎所有 Internal Slot 保存的都是一些抽象数据，例如：

- Boolean
    
- Number
    
- Object Reference
    
- List
    
- Record
    
- ECMAScript Value
    

它们共同描述的是：

> **对象当前处于什么状态（State）。**

至于这些状态应该如何变化、对象收到外部操作后应该如何响应，则属于另外一套机制，我们后面再讨论。

---

## 为什么 Internal Slot 不能设计成普通 Property？

很多人第一次看到 Internal Slot 时都会想到一个问题：既然它们本质上也是数据，那为什么不直接做成普通 Property？例如：

```javascript
obj.internalPrototype
obj.internalPromiseState
```

这样不是更简单吗？

原因在于：

> **Internal Slot 保存的是对象运行时必须保持一致性的状态，而不是普通数据。**

以 Promise 为例。

`[[PromiseState]]` 保存 Promise 当前的状态：

```text
pending
fulfilled
rejected
```

如果它只是普通 Property，任何代码都可以直接：

```javascript
promise.internalPromiseState = "fulfilled";
```

但 Promise 的状态变化，从来都不是一次简单赋值。每一次状态迁移，同时意味着：

- 调度所有已经注册的 reaction；
    
- 将任务放入微任务队列；
    
- 保证状态只能从 pending 单向进入 settled；
    
- 清理内部等待队列。
    

换句话说，状态变化本身只是结果，真正重要的是状态变化伴随的一整套规范算法。

如果允许开发者直接修改状态，就可能出现：

- Promise 已经 fulfilled，但 `.then()` 从未执行；
    
- Promise 已经 rejected，却还能再次变成 pending；
    
- reaction 被重复调度或完全遗漏。
    

整个 Promise 状态机都会失去一致性。

所以规范并没有把这些状态暴露出来，而是要求：

> **只能通过规范定义的入口修改它们。**

例如：

```javascript
resolve(value);
reject(reason);
```

开发者操作的是 API，而不是内部状态本身。

还有一个容易被忽略的区别。

Property 的变化属于属性系统，因此它会受到 Property Descriptor 的约束。例如：

```javascript
writable: false
```

会使赋值失败。

而 Internal Slot 根本不属于属性系统。它不参与：

- Property Descriptor；
    
- Property 查找；
    
- 枚举；
    
- 删除；
    
- getter/setter；
    
- Proxy 的属性拦截。
    

也就是说，它拥有一套完全独立于 Property 的生命周期。

因此，ECMAScript 引入 Internal Slot，并不仅仅是为了“隐藏实现细节”。更准确地说，是为了建立一道语义边界：

> **对象的运行状态，只能由规范定义的算法维护，而不能被外部代码随意修改。**

开发者虽然无法直接访问 Internal Slot，却几乎每天都在间接使用它们：

- `Object.getPrototypeOf(obj)` 读取的是 `[[Prototype]]`；
    
- `Object.isExtensible(obj)` 读取的是 `[[Extensible]]`；
    
- `promise.then(...)` 内部依赖的是 `[[PromiseState]]`。
    

这些 Internal Slot 从来不会出现在我们的代码里，但它们却一直在默默支撑着整个 JavaScript 对象模型。

---

## 不同对象，拥有不同的 Internal Slot

并不是所有对象都拥有同样一套 Internal Slot。不同类型的对象，会拥有各自专属的内部状态。

- 普通对象通常拥有：`[[Prototype]]`、`[[Extensible]]`
    
- Promise 拥有：`[[PromiseState]]`、`[[PromiseResult]]`、`[[PromiseFulfillReactions]]`、`[[PromiseRejectReactions]]`
    
- Map 拥有：`[[MapData]]`
    
- Set 拥有：`[[SetData]]`
    
- Generator 拥有：`[[GeneratorState]]`
    
- RegExp 拥有：`[[OriginalSource]]`、`[[OriginalFlags]]`
    
- Date 拥有：`[[DateValue]]`
    

可以发现，ECMAScript 真正关心的并不是某个 `class` 名称，而是：

> **这个对象拥有哪些 Internal Slot。**

Promise 为什么是 Promise？

因为它拥有 Promise 所要求的那组 Internal Slot。

Map 为什么是 Map？

因为它拥有 Map 所要求的那组 Internal Slot。

Date 为什么是 Date？

因为它拥有 `[[DateValue]]`。

甚至很多内置对象的方法，都会首先检查对象是否拥有某个特定的 Internal Slot。例如：

```javascript
Map.prototype.get.call({}, "x");
```

会抛出：

```text
TypeError
```

因为 `{}` 并不拥有 `[[MapData]]`。

类似地：

```javascript
Date.prototype.getTime.call({});
```

也会抛出异常，因为 `{}` 没有 `[[DateValue]]`。

因此，对于 ECMAScript 而言，一个对象是什么类型，本质上并不是由 `constructor` 或 `instanceof` 决定的，而是由它拥有哪些 Internal Slot 决定的。

---

## Internal Method：对象真正的行为规则

到目前为止，我们讨论的都是：

> 对象保存了什么状态（State）。

但仅仅知道对象拥有怎样的状态，还不足以解释对象为什么会表现出各种行为。

例如：

- `[[Prototype]]` 保存当前对象的原型引用，但不会自己沿着原型链查找属性；
    
- `[[PromiseState]]` 保存 Promise 当前状态，但不会自己调度 `.then()` 回调；
    
- `[[MapData]]` 保存 Map 的键值记录，但不会自己查找、插入和删除元素。
    

这些行为都由另一套机制负责：

> **Internal Method（内部方法）。**

可以简单理解成：

```text
Internal Slot   → 记录状态（State）
Internal Method → 定义行为（Behavior）
```

Internal Method 会读取、修改并维护 Internal Slot。

因此：

- Property 是对象暴露出来的数据；
    
- Property Descriptor 描述 Property 的特征；
    
- Internal Slot 保存对象的状态；
    
- Internal Method 定义对象的行为。
    

明确了这四者的分工之后，一个容易被忽略的事实是：

> **几乎所有 JavaScript 语法，最终都会转化为对某个 Internal Method 的调用。**

很多开发者会觉得：

```javascript
obj.foo
```

就是“读取一个属性”。

但 ECMA-262 并不会这样描述。

规范真正描述的是：

```text
obj.foo

↓

调用对象的 [[Get]]
```

同样：

- `obj.foo = 1` → 调用 `[[Set]]`
    
- `delete obj.foo` → 调用 `[[Delete]]`
    
- `fn()` → 调用 `[[Call]]`
    
- `new Foo()` → 调用 `[[Construct]]`
    

可以发现，ECMAScript 并不是围绕 JavaScript 语法描述对象行为。恰恰相反，它先定义：

> **一个对象应该实现哪些 Internal Method。**

然后再规定：

> **某种 JavaScript 语法，会触发哪个 Internal Method。**

整个关系可以表示成：

```text
JavaScript Syntax

↓

Internal Method

↓

读取 Property Descriptor
读取 Internal Slot

↓

执行规范算法

↓

返回结果
```

因此，很多文章会说：

> JavaScript 操作 Property。

但更准确地说应该是：

> **JavaScript 语法触发 Internal Method，而 Internal Method 再操作 Property 与 Internal Slot。**

例如：

```javascript
obj.foo
```

真正发生的过程更接近：

```text
obj.foo

↓

[[Get]]

↓

查找 Property Descriptor

↓

如果存在 Data Property
读取 [[Value]]

↓

返回结果
```

如果对象自身没有该属性：

```text
[[Get]]

↓

读取 [[Prototype]]

↓

沿原型链继续调用 [[Get]]
```

直到找到属性，或者到达 `null`。

如果找到的是 Accessor Property：

```text
[[Get]]

↓

读取 Descriptor.[[Get]]

↓

调用 Getter Function
```

整个过程中：

- Property Descriptor 描述属性长什么样；
    
- `[[Prototype]]` 提供原型链状态；
    
- 真正驱动整个过程的，则是 `[[Get]]`。
    

这也是前面三组概念第一次真正协同工作的地方：

```text
Internal Method
      ↓
操作
      ↓
Property Descriptor
      +
Internal Slot
```

---

## 所有普通对象，都实现了一套 Essential Internal Methods

Internal Method 并不是每个对象随意定义的。

ECMAScript 要求：

> **所有 Ordinary Object（普通对象）都必须实现一组 Essential Internal Methods（基本内部方法）。**

这意味着，只要是普通对象，无论它看起来是什么样子，都拥有同一套基础行为。

其中最核心的一组包括：

```text
[[GetPrototypeOf]]
[[SetPrototypeOf]]
[[IsExtensible]]
[[PreventExtensions]]
[[GetOwnProperty]]
[[DefineOwnProperty]]
[[HasProperty]]
[[Get]]
[[Set]]
[[Delete]]
[[OwnPropertyKeys]]
```

几乎所有 JavaScript 日常操作，最终都会落到这些内部方法上：

```text
obj.foo
        ↓
      [[Get]]

obj.foo = 1
        ↓
      [[Set]]

delete obj.foo
        ↓
      [[Delete]]

Object.keys(obj)
        ↓
 [[OwnPropertyKeys]]
        ↓
过滤不可枚举属性

Object.defineProperty(...)
        ↓
[[DefineOwnProperty]]
```

从这个角度看：

> JavaScript 语法只是入口，Internal Method 才是对象真正执行行为的地方。

---

## Property Descriptor 与 Internal Method 是如何协作的？

这里正好可以和上一篇的 Property Descriptor 衔接起来。

很多人容易理解为：

```javascript
Object.defineProperty()
```

修改的是某个 Property。

但更准确地说，它做的是：

> **构造一份新的 Property Descriptor，并将它交给对象的 `[[DefineOwnProperty]]`。**

例如：

```javascript
Object.defineProperty(obj, "foo", {
  value: 1,
  writable: false,
});
```

规范真正处理的信息更接近：

```text
Property Key: "foo"

Property Descriptor
├── [[Value]] = 1
├── [[Writable]] = false
├── [[Enumerable]] = false
└── [[Configurable]] = false
```

随后：

```text
[[DefineOwnProperty]]

↓

检查对象当前状态
检查已有属性状态
检查 Descriptor 是否合法
决定是否允许定义

↓

更新 Property
```

这里的职责划分非常清晰：

```text
Property Descriptor
        ↓
描述“要定义成什么样”

[[DefineOwnProperty]]
        ↓
决定“能不能这样定义”
```

或者更完整地说：

```text
Property Descriptor
        ↓
提供规则输入

Internal Method
        ↓
执行规范算法

Internal Slot
        ↓
提供对象当前状态

↓

最终决定结果
```

这也是 ECMAScript 对象模型最核心的一条运行链路：

```text
JavaScript Syntax
        ↓
Internal Method
        ↓
Property Descriptor + Internal Slot
        ↓
Specification Algorithm
        ↓
Result
```

理解了这条链路，后面的数组、函数对象、Proxy、Promise 等各种特殊对象，本质上都只是：

> 拥有不同的 Internal Slot，并实现了不同的 Internal Method 行为而已。

## 为什么数组这么特殊？

回到开头的问题——为什么 `arr.length = 2` 会删除元素？答案不在于 `length` 本身，而在于 ECMAScript 对对象的另一种分类。

---

### Ordinary Object 与 Exotic Object

ECMAScript 并没有把所有对象都视为完全相同。规范将对象分成两大类：

- **Ordinary Object（普通对象）**：使用默认的 Internal Method 实现。
- **Exotic Object（特殊对象）**：重写了其中一个或多个 Internal Method，从而表现出与普通对象不同的行为。

二者最大的区别，不在于 Property，也不在于 Internal Slot，而在于：**实现 Internal Method 的方式不同。**

普通对象直接使用规范给出的默认算法，例如 `[[Get]]`、`[[Set]]`、`[[Delete]]`、`[[DefineOwnProperty]]`、`[[OwnPropertyKeys]]`。因此，无论何时，对普通对象的赋值都遵循同一套规则。

Exotic Object 则不同，它会重写某些 Internal Method。数组就是最经典的例子。除此之外，还有 Proxy、String 包装对象、Module Namespace 对象、Arguments 对象、TypedArray 等，它们都属于 Exotic Object，只是各自重写的 Internal Method 不同，因此表现出的能力也完全不同。

可以这样理解：

> Ordinary Object → 使用默认 Internal Method  
> Exotic Object → 重写部分 Internal Method

也就是说，ECMAScript 并不是通过“特殊 Property”创造特殊对象，而是**通过重写 Internal Method，让对象拥有不同的行为。**

---

### 普通对象修改 Property，会发生什么？

先来看最普通的对象：

```javascript
const obj = { a: 1 };
obj.b = 2;
```

很多人脑海里的过程可能只有一句“新增一个属性”，但规范中的实际过程是这样一连串调用：

```text
obj.b = 2
  ↓
[[Set]]
  ↓
构造新的 Property Descriptor
  ↓
[[DefineOwnProperty]]
  ↓
新增 Property
```

比如 `obj.b = 2` 最终会生成一份 Data Property Descriptor：

```text
Property: "b"
Descriptor:
  [[Value]] = 2
  [[Writable]] = true
  [[Enumerable]] = true
  [[Configurable]] = true
```

`[[Set]]` 把这套 Descriptor 交给 `[[DefineOwnProperty]]`，由后者决定能否新增、是否覆盖已有属性等。整个过程只是：

```text
[[Set]] → [[DefineOwnProperty]] → 更新 Property Descriptor
```

除此之外，不会发生任何额外行为。所以 `obj.count = 2` 不会影响 `obj.a`，也不会删除其他属性——普通对象的 `[[DefineOwnProperty]]` 没有任何特殊规则。

---

### 数组为什么不同？

数组当然也是对象，因此 `arr.length = 2` 同样会先进入 `[[Set]]`，这一点与普通对象没有区别。**真正开始不同的，是下一步。**

普通对象会继续调用默认的 `[[DefineOwnProperty]]`，而数组作为 **Array Exotic Object**，重写了自己的 `[[DefineOwnProperty]]`。也就是说：

- 普通对象：`[[Set]]` → 默认的 `OrdinaryDefineOwnProperty`
- 数组：`[[Set]]` → **数组专属的 `[[DefineOwnProperty]]`**

这就是两者行为分叉的起点。数组的 Property Descriptor 结构仍然完全符合统一定义——真正特殊的是：**数组自己的 `[[DefineOwnProperty]]`，会根据不同的 Property Key 执行不同的规范算法。** 例如，处理”普通索引”时，它需要维护 `length`；处理 `length` 本身时，又会进入一套专门逻辑。

---

### 为什么修改 length 会进入 `ArraySetLength`？

现在来梳理 `arr.length = 2` 的真实过程：

```text
arr.length = 2
  ↓
[[Set]]
  ↓
构造新的 Property Descriptor（[[Value]] = 2）
  ↓
Array 的 [[DefineOwnProperty]]
  ↓
判断 Property Key
  ↓
Key == "length" → 是
  ↓
进入 ArraySetLength 算法
```

`[[Set]]` 构造出的 Descriptor 只是表示”希望把 `length` 更新为 2”，本身没有任何神奇之处。真正特殊的是：数组的 `[[DefineOwnProperty]]` 判断出 Key 是 `length` 后，进入了规范专门定义的 `ArraySetLength` 算法。`ArraySetLength` 只是 `[[DefineOwnProperty]]` 内部执行的一段规范算法，两者并不是同一个概念。

---

## ArraySetLength 到底做了什么？

`ArraySetLength` 的核心思想可以归纳为三步：

1. 检查新的 `length` 是否合法。
2. 如果长度变大，只更新 `length`，不创建新元素。
3. 如果长度变小，删除超出的属性（Property），再更新 `length`。

---

### 第一步：检查新的 length 是否合法

很多人以为：

```javascript
arr.length = xxx;
```

只是一次普通赋值。实际上，它会先经过一整套合法性检查。

* 设置负值会直接抛出 `RangeError`：
  ```javascript
  arr.length = -1;   // RangeError
  ```
* 非整数同样失败：
  ```javascript
  arr.length = 1.5;  // RangeError
  ```
* `NaN` 也会被拒绝：
  ```javascript
  arr.length = NaN;  // RangeError
  ```

这是因为 ECMAScript 要求数组长度必须是一个合法的 **Array Length**，即满足：

```
0 ≤ length ≤ 2³² − 1
```

并且必须是整数。  
所以 `4294967295` 合法，而 `4294967296` 会抛出 `RangeError`。

可以看到，数组修改 `length` **并不是“先赋值，再检查”**，恰恰相反——只有新值通过规范规定的检查后，后续流程才会继续执行。

---

### 第二步：比较新旧长度

通过合法性检查后，规范会读取数组当前长度（`oldLength`），并与新长度（`newLength`）进行比较。整个过程可以简化成：

```
oldLength → newLength
   ↓
newLength ≥ oldLength ?
```

### 如果 `newLength ≥ oldLength`（数组变长）

假设：

```javascript
const arr = [1, 2];
arr.length = 10;
```

很多初学者会认为 JavaScript 会自动补齐成 `[1, 2, undefined, undefined, ...]`，**实际上并不会**。输出仍然是：

```javascript
console.log(arr);  // [1, 2, <8 empty items>]
```

原因在于：**数组变长，并不会自动创建新的 Property**。  
规范真正做的，只是更新了 `length` 属性，告诉对象：“现在允许出现索引 `0 ~ 9`”。

至于索引 `2`、`3`、...、`9` 对应的 Property，根本还不存在。因此：

```javascript
2 in arr;          // false
Object.hasOwn(arr, 2);  // false
```

访问 `arr[2]` 得到 `undefined`，并不能说明 Property `"2"` 一定存在——那只是原型链查找不到时的默认返回。这也就是为什么「空洞数组（Sparse Array）」能够存在：  
**数组长度描述的是可用索引范围，而不是实际拥有多少个 Property。**  
这是数组区别于普通对象的重要特性之一。

---

### 第三步：删除超出的 Property

真正复杂的部分，是 **`newLength < oldLength`** 的情况。

例如：

```javascript
const arr = [1, 2, 3, 4];
arr.length = 2;
```

此时 `oldLength = 4`，`newLength = 2`。  
规范并不会直接修改 `length = 2`，因为那样会立即产生矛盾：对象仍拥有 Property `"2"` 和 `"3"`，但 `length` 却声明最大合法索引应小于 `2`。

因此，规范采用了**相反的顺序**：先删除 Property，再更新 `length`。

```
oldLength = 4
   ↓
删除 Property "3"
   ↓
删除 Property "2"
   ↓
更新 length 属性
   ↓
完成
```

这里有一个很容易被忽略的关键点：规范强调的是 **Delete Property**，而不是“把值改成 `undefined`”。

删除之后：

```javascript
arr[2];      // undefined
2 in arr;    // false
```

而如果只是：

```javascript
arr[2] = undefined;
2 in arr;    // true
```

从 Property Descriptor 的角度看，它们完全不同：

* 删除：Property 已不存在。
* 赋值为 `undefined`：Property 仍在，只是 `[[Value]]` 为 `undefined`。

> **ArraySetLength 删除的是 Property，而不是 Property 的值。**

---

### 一个很多文章都会忽略的细节：ArraySetLength 具有”回滚”能力

真正让 `ArraySetLength` 精彩的，并不是删除元素，而是规范为了保证数组始终保持一致，专门设计的一套**回滚（Rollback）机制**。

来看一个例子：

```javascript
const arr = [1, 2, 3];

Object.defineProperty(arr, “2”, {
  configurable: false,
});
```

现在 `Property “2”` 已经不能再被删除。

接着执行：

```javascript
arr.length = 1;
```

如果按最朴素的思路，过程似乎是：  
`length = 1` → 删除索引 2 → 结束。  
但规范并不会这样做。真正的执行顺序是：

1. 收到新的 `length` Property Descriptor
2. 进入 `ArraySetLength`
3. 尝试删除 `Property “2”`
4. 删除失败 → 终止 → 恢复 `length`

删除失败之后，规范会立即终止整个算法。如果继续把 `length = 1` 写回数组，对象就会进入非法状态：`length = 1`，但 `Property “2”` 仍然存在。这违反了数组的基本约束，整个过程更像数据库事务（Transaction）：所有步骤成功，才提交结果。

#### 回滚的本质：Descriptor 的约束与数组的一致性

为什么删除会失败？原因在 `Object.defineProperty(arr, “2”, { configurable: false })` 之后，对应 Property Descriptor 的 `[[Configurable]]` 变成了 `false`。删除 Property 时，删除算法会首先检查 `[[Configurable]]`，只有 `true` 才允许——真正控制删除是否成功的，始终是 **Property Descriptor**，而不是数组。

那为什么删除失败后必须回滚，而不是”保留 `length = 1`、剩下的 Property 留着”？因为对于数组，`length` 还承担着描述索引边界的职责。如果 `length = 1` 而 `Property “2”` 仍然存在，对象就进入了自相矛盾的状态——规范不允许这种不一致。

因此 `ArraySetLength` 最核心的目标并不是维护 `length` 属性本身，而是维护**整个数组对象的一致性（Consistency）**。

#### 理解 ArraySetLength，其实就是理解 Internal Method

回头再看 `arr.length = 2`，整个过程已经非常清楚了。  
JavaScript 代码 `arr.length = 2` 并不是“修改一个数字”，真正发生的是：

```
JavaScript 语法
   ↓
[[Set]]
   ↓
构造新的 Property Descriptor
   ↓
Array [[DefineOwnProperty]]
   ↓
ArraySetLength
   ↓
检查合法性
   ↓
必要时删除 Property
   ↓
更新 length Property
```

可以看到，整个过程中真正负责判断、删除、回滚、更新 `length` 的，全部都是 `Array` 的 `[[DefineOwnProperty]]` 与 `ArraySetLength`——真正执行规则的是 Internal Method。

理解了 ArraySetLength 如何通过 Internal Method 驱动行为，就抓住了理解 Proxy 和 Reflect 的关键。下一篇 [[JavaScript/js-object-model-04|JavaScript 对象模型（四）]] 会深入展开：Proxy 如何通过替换 Internal Method 来接管对象行为，Reflect 又如何将 Internal Method 的语义暴露给开发者——两者看似不同，本质上服务于同一个对象模型。

---

## 重新理解 ECMAScript 的对象模型

现在，我们终于可以把整篇文章串起来了。

很多开发者眼中的对象，大概是一组 Key-Value。正如上一篇所述，这并不准确——每个 Property 对应一份 Property Descriptor。

但直到这一篇，我们才真正补全了整个对象模型。  
对于 ECMAScript 来说，一个对象更接近下面这样的结构：

```
                 Object
                    │
     ┌──────────────┴──────────────┐
     │                             │
     ▼                             ▼
 Properties                 Internal Slots
     │                             │
     ▼                             │
Property Descriptor                 │
     │                             │
     └──────────────┬──────────────┘
                    ▼
            Internal Methods
                    │
                    ▼
            执行规范定义的算法
                    │
                    ▼
              得到最终行为
```

这里有一点和很多文章的画法不同：我把 **Internal Method 放在最下面**。  
因为它并不是对象保存的一部分数据，而是 **对象响应各种操作时真正执行的行为**。

---

## 再回头看几个熟悉的例子

| 场景 | JavaScript 语法 | 核心调用链 |
|------|----------------|-----------|
| 读取属性 | `obj.foo` | `[[Get]]` → 查找 Property Descriptor → 读 `[[Prototype]]` 沿原型链 |
| 修改数组长度 | `arr.length = 2` | `[[Set]]` → `Array [[DefineOwnProperty]]` → `ArraySetLength` |
| 函数调用 | `foo()` | `[[Call]]` → 执行函数体 |
| 构造函数 | `new Foo()` | `[[Construct]]` → 创建实例 → 执行构造过程 |

每个场景都是同一个模式：**JavaScript 语法 → Internal Method → 读取 Descriptor / Slot → 返回结果**。

## 附录

### 附录 A：Internal Slot 规范抽象与 Private Field

**Internal Slot 是规范抽象，不是引擎实现**

另一个常见误解是：V8 里面一定有一个名字就叫 `[[Prototype]]` 的字段。

其实并不是。ECMAScript 从来不会规定 JavaScript 引擎应该如何存储这些状态。规范真正规定的是：**对象在逻辑上必须拥有这些状态，并且对象行为必须符合规范定义。** 至于这些状态最终是如何保存的，则完全属于引擎自己的实现细节。例如，它可能是一个隐藏字段、一块独立的内存区域、一个指针、Hidden Class、Shape、Descriptor，或其它任何能够满足规范要求的数据结构。

因此：**Internal Slot 是一种规范抽象（Specification Abstraction），而不是某种固定的数据结构。** 这也是 ECMAScript 一直坚持的设计原则：**规范定义行为，引擎决定实现。** 正因为规范与实现相互解耦，不同 JavaScript 引擎才能采用完全不同的内部结构，却依然表现出一致的 JavaScript 行为。

**Private Field ≠ Internal Slot**

学习 Internal Slot 时，很多人会联想到 ES2022 引入的 Private Field：

```javascript
class Person {
  #name = "Tom";
}
```

这里的 `#name` 是不是也是 Internal Slot？答案是：**不是。**

两者虽然都具有"隐藏"这一特点，但隐藏的原因完全不同：

- **Private Field** 是 JavaScript 语言特性，开发者可以通过 `#` 语法在类内部访问，只是访问范围受到语法规则限制。类外部访问 `person.#name` 会直接产生语法错误。
- **Internal Slot** 是 ECMAScript 规范抽象，`obj.[[Prototype]]` 根本不是合法语法，即使写成 `obj["[[Prototype]]"]`，访问到的也只是一个普通 Property。

| Private Field     | Internal Slot       |
| ----------------- | ------------------- |
| JavaScript 语言特性   | ECMAScript 规范抽象     |
| 可以通过 `#` 语法访问     | 没有任何对应语法            |
| 属于对象公开语义的一部分      | 属于对象运行时内部状态         |
| JavaScript 可以直接读写 | JavaScript 永远无法直接访问 |

两者虽然都体现了"封装"的思想，但服务的目标完全不同——一个面向开发者，一个面向语言规范。

### 附录 B：ArraySetLength 倒序删除的健壮性考量

正文提到 `ArraySetLength` 删除元素时采用**倒序**（从最大索引向前删除），这个设计并非随意选择。

假设有一个数组 `[1, 2, 3, 4]`，需要收缩到 `length = 2`，要删除索引 `2` 和 `3`。  
如果从后向前（先删 `3`，再删 `2`）：

* 无论何时，当前数组的长度都不会与剩余 Property 发生冲突，整个对象始终保持一致。

更重要的是，规范还需处理删除失败的情况。倒序删除可以保证：**一旦某次删除失败，剩余未删除的 Property 仍保持连续**，为后续的回滚（Rollback）机制铺路。

因此规范选择 **从 `oldLength - 1` 一直删除到 `newLength`**，这个顺序并非随意设计，而是为复杂边界情况下的健壮性服务。

### 附录 C：三种 `[[...]]`，并不是同一种东西

很多人第一次阅读 ECMA-262 时都会产生一个误解。

例如：

```text
[[Prototype]]
[[PromiseState]]
[[Value]]
[[Writable]]
[[Get]]
[[Delete]]
```

它们全部写成 `[[...]]`，于是很容易认为它们是不是同一类东西。

其实不是。

双中括号 `[[...]]` 只是 ECMAScript 规范的一种命名记号，并不表示某种统一的数据结构。

这些名字实际上代表三类完全不同的概念：

- **Internal Slot**：保存状态，例如 `[[Prototype]]`、`[[PromiseState]]`、`[[MapData]]`、`[[Extensible]]`
    
- **Internal Method**：定义行为，例如 `[[Get]]`、`[[Set]]`、`[[Delete]]`、`[[Call]]`、`[[Construct]]`、`[[DefineOwnProperty]]`
    
- **Property Descriptor Field**：描述 Property 的特征，例如 `[[Value]]`、`[[Writable]]`、`[[Enumerable]]`、`[[Configurable]]`，以及访问器属性中的 `[[Get]]`、`[[Set]]`
    

三者分别回答的是三个完全不同的问题：

- **Property Descriptor** 回答：这个 Property 是什么样的？
    
- **Internal Slot** 回答：对象当前处于什么状态？
    
- **Internal Method** 回答：对象收到操作后应该如何响应？
    

最后，可以把 ECMAScript 对象模型概括成下面这张图：

```text
对象（Object）

├── 对外的数据
│
│   └── Property
│          └── Property Descriptor
│
└── 对内的运行机制
     ├── Internal Slot     （State）
     └── Internal Method   （Behavior）
```

这也是阅读 ECMA-262 时最重要、也最容易混淆的一组概念。

## 总结

文章开头，我们提出了一个问题：

> 为什么 `arr.length = 2` 会删除数组元素？

现在，这个问题已经有了完整的答案。  
答案不在 `length` 本身：**数组作为一种 Array Exotic Object，重写了 `[[DefineOwnProperty]]`**。  
因此，当执行 `arr.length = 2` 时，规范真正执行的是：

```
JavaScript 语法
   ↓
[[Set]]
   ↓
构造 Property Descriptor
   ↓
Array [[DefineOwnProperty]]
   ↓
ArraySetLength
   ↓
检查合法性
   ↓
删除多余 Property
   ↓
更新 length Property
```

整个过程远比一次普通赋值复杂得多。

但更重要的是——如果我们只停留在这个结论上，我们就只看到了数组。

## 真正值得记住的，不是数组，而是 ECMAScript 的对象协议

ECMAScript 从来不是一门“操作属性”的语言，而是一门**“触发对象协议（Object Protocol）”的语言**。

每一行我们写下的 JavaScript 语法，最终都会转化成对 Internal Method 的调用。Internal Method 再结合 Property Descriptor 与 Internal Slot，决定对象应该表现出什么行为。

- **Property 是接口**，开发者通过它和对象对话；
- **Property Descriptor 是元数据**，描述了属性的一切特征；
- **Internal Slot 是状态**，保存对象运行时的内部信息；
- **Internal Method 是行为协议**，定义了对象如何回应每一个操作。

理解这一点，也就理解了为什么数组可以删除元素、函数可以被调用、Promise 可以维护状态、Proxy 可以接管对象行为。

它们看起来是不同的语言特性，但在 ECMAScript 的视角里，它们只是同一个对象模型的不同实现：**每种 Exotic Object 通过重写一组 Internal Method，表达出自己的独特语义，而 Property Descriptor 和 Internal Slot 永远是这些语义的基石。**

Property 只是露出水面的那一部分。真正驱动整个 JavaScript 语言运行的，是水下的三层抽象——**元数据（Descriptor）、状态（Slot）、行为协议（Method）**。这三者，构成了 ECMAScript Object Protocol。

而这，也正是 ECMAScript 对象模型真正迷人的地方。🌊
